# 03 Host CSR Enrollment

## Why this matters

For production, `hosting service` onboarding must not stop at business activation.
It also needs a proper PKI step for the host's technical Fabric identity.

## Separation of concerns

- license / exchange / activation:
  authorizes that a host may request network identity
- CSR:
  carries the host public key that must be signed
- signed certificate chain:
  becomes the technical Fabric/X.509 identity of that host

## Recommended production flow

1. The host completes a license or activation flow with ICA.
2. ICA validates region, domain, role, capabilities, and policy.
3. The host generates its private key locally.
4. The host generates a CSR locally.
5. The host submits CSR plus license/evidence metadata to ICA.
6. ICA validates policy and calls internal `fabric-ca`.
7. ICA returns the signed leaf certificate and CA chain.
8. The host stores the private key locally or in KMS/HSM and uses the cert to connect.

## Security rules

- The host private key should not be generated by ICA in production.
- `fabric-ca` should stay private and should not be Internet-facing.
- `dataspace-ica-ts` should be the public API and policy layer.
- DID/JWKS/discovery artifacts can be public; internal CA enrollment paths should not be.

## Suggested endpoint shape

1. `POST .../hosting-service/_exchange`
2. `POST .../hosting-service/csr/_activate`
3. `POST .../hosting-service/csr/_activate-response`

## Current simplification

The current simplified model remains:

- hosts hold direct Fabric client identity
- tenants publish through host services
- tenants can remain without direct Fabric client certificates

Current documentation scope for animal onboarding:

- in ICA docs, keep the animal domain described here limited to `animal-pet-global`
- do not expand this document into future veterinary segmentation or future regional channel naming
- those decisions belong outside ICA, primarily in domain-extension SDKs and architecture notes
